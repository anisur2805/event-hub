# Event Hub — Decisions Log

One line each: decision + reason. Ordered by when made.

1. Plugin lives at `wp-content/plugins/event-hub/` inside this Local site (spec said "this directory"; a WP plugin must be in the plugins dir to activate; site also serves as the wp-env-style test env). Conservative pick: use the real site + Docker where needed.
2. Gated endpoints use capability `edit_others_posts` (spec-mandated) — no custom caps; keeps roles mapping default (admin/editor).
3. Meta keys stored prefixed as `eh_start`, `eh_end`, `eh_venue`, `eh_capacity` (rest-exposed under `meta.eh_start` etc. plus normalized camelCase in our /events route). Prefix hygiene per WP standards; field names in REST contracts are camelCase.
4. RSVP submission requires JS. Server-rendered display (list, cards, counts, ICS) works with JS disabled; the POST is an SPA-style fetch through the Interactivity store. A `<noscript>` notice explains this. Conservative because there is no non-JS fallback endpoint in scope (no admin-post fallback without duplicating the REST surface).
5. Capacity enforcement = single atomic `INSERT … SELECT … WHERE` against the custom table (re-checks capacity inside the INSERT; UNIQUE(event_id,email) handles duplicates). Avoids check-then-insert race; no explicit transactions needed (single-statement atomicity + unique key). Verified by Phase 5 race tests.
6. Block styles use only `var(--wp--preset--*)` tokens with safe fallbacks declared on a scoped class (not `:root` — avoids leaking into theme typography); degrades sanely in classic themes.
7. `build/` is built locally/CI, not committed in the repo; for this live-site test run the build is produced by `npm run build` and present on disk. wp-env quickstart in README covers the build step.
8. Composer autoload used when `vendor/autoload.php` exists; otherwise a tiny SPL autoloader fallback (`EventHub\` → `includes/class-*.php`) so the production plugin has zero required dev files.
9. ICS served via REST route (`/event-hub/v1/event/{id}/calendar.ics`) instead of rewrite endpoints — no flush rewrite complexity, nonce-free public GET, same escaping path testable via `rest_do_request`.
10. `@wordpress/scripts` 37.x with `--experimental-modules` for Interactivity Script Module builds (viewScriptModule in block.json, WP 6.5+ requirement).
11. Load-test tooling stays inside the WP/Node toolchain already present (xargs -P curl loops + WP-CLI seed), per spec (no k6).
12. `wp-env` is used if Docker networking allows; otherwise tests run against this Local site via WP-CLI + a dedicated test install (WP_TESTS_DIR via wp-env image). Logged concretely in the report.
13. RSVP submit button is a type="button" with iAPI click handler (+ noscript hint). A no-JS form POST fallback is out of scope (would need a second public endpoint surface).
14. Capacity write = GET_LOCK(advisory, 2s) + single INSERT…SELECT that re-checks capacity inside SQL, + UNIQUE(event_id,email) for duplicates. Advisory lock serializes same-event writes to avoid the COUNT-then-INSERT window; different events never contend.
15. File naming: PSR-4 requires `Plugin.php` = `EventHub\Plugin`, but WPCS sniff "WordPress.Files.FileName.InvalidClassFileName" expects class-plugin.php. Project rule: PSR-4 wins; phpcs.xml excludes that sniff for includes/. Logged so reviewers don't "fix" it back.
16. i18n: PHP text domain `event-hub`; JS uses the same domain via wp-scripts (@wordpress/i18n auto textdomain-plugin). All user-facing strings in both PHP and JS translatable.
20. Admin CSV export URL contract: PHP provides `window.eventHubAdmin.exportBaseUrl` (admin-post.php base with `action=eh_export_rsvps`, no params) + `exportNonce` (action `eh_export_rsvps`); the React app appends `event_id` + `_wpnonce` at click time so the export always matches the selected event. Frontend also expects `restUrl`, `nonce`, `events: [{id,title}]`, `initialEventId` in the same object.
21. Event-list category filter: filtered cards are rebuilt client-side by cloning the server-rendered `<template data-eh-card-tpl>` inside the list region; slots (`data-eh-slot="title|titlelink|datetime|venue|excerpt|count|link"`) get `textContent`/checked-`href` only — REST strings are never parsed as HTML (XSS-safe by construction). Filtered cards expose a plain permalink link styled as the RSVP button instead of an inline iAPI form (no store re-wiring in JS); the unfiltered initial render keeps the full server-rendered RSVP form. The select sits in a GET `<form>` (with JS: `actions.filterSubmit` prevents default; without JS: native reload preserving the category). REST base/nonce reach the filter through `wp_interactivity_state()` via the store `state`, not DOM scraping.
22. iAPI store registration is split: `src/interactivity/store.ts` registers `event-hub` (RSVP actions, getters, `setName`/`setEmail`); `src/blocks/event-list/filter.ts` re-calls `store()` with just `filterCategory`/`filterSubmit`, which deep-merges into the namespace. rsvp-button and event-list view entries both import the same modules, so a page with both blocks registers the store exactly once; markup can reference the filter actions only inside the list region whose view entry includes filter.ts.
17. Test env: official @wordpress/env 12.x pinned as devDependency (the npm package name `wp-env` is an unrelated squatter package — npx wp-env runs the wrong thing). wp-env core pinned WordPress/WordPress#7.1.3 with SCRIPT_DEBUG + SAVEQUERIES on.
18. PHPCS scan scope: plugin PHP only (vendor/build/tests excluded); test bootstrap legitimately uses fwrite before WP loads, and PSR-4 class filenames are excluded per #15.
19. (backend) Render_Blocks buttons: one visible primary button per state — `data-wp-on--click="actions.rsvpGoing"` by default; when capacity is full (context `full=true`) the same wrapper renders `actions.rsvpWaitlist` as "Join waitlist" instead. Two distinct action names instead of a data-attribute arg keeps the iAPI store flat (`actions.rsvpGoing`/`actions.rsvpWaitlist` both call the shared submit with the status baked in); documented as the one-line comment inside `Render_Blocks::render_rsvp_button()`.

21. (backend) Duplicate detection: pre-check `find_existing()` inside the GET_LOCK, returning `eh_duplicate` for the common case regardless of requested status/capacity; the UNIQUE(event_id,email) key stays the authoritative race guard and maps to the same code. Rationale: a going-request onto an event with a going-full-but-email-exists state short-circuits in the INSERT's WHERE clause, so no SQL error fires and error text sniffing alone cannot distinguish duplicate vs full.

Cookieless clients (stateless) proceed without nonce and are covered by the 10/10min/IP transient rate limit (429 `eh_rate_limited`, Retry-After sent via a `rest_pre_serve_request` filter because WP core never promotes WP_Error data to response headers).

(integration) Every PHP seed of `restUrl` used `rest_url('event-hub/v1')` (namespaced) while all three JS consumers template `${restUrl}event-hub/v1/...` — browser fetches doubled the namespace (`/wp-json/event-hub/v1event-hub/v1/rsvp` -> 404) and the admin screen showed "Could not load RSVPs". 33. (backend) Waitlist auto-promotion lives in `Rsvp_Repository::delete_and_promote()` — one advisory-lock window hosting DELETE + promotion, never two calls. The promotion is a single guarded UPDATE whose WHERE re-counts `going` against the live `eh_capacity` meta (same predicate shape as create()'s INSERT…SELECT), so a capacity lowered below the existing going count blocks the flip (no overflow on admin cleanup). Target = earliest `waitlist` by `created_at ASC, id ASC`; delete of a waitlist row promotes nothing. `event_hub_rsvp_promoted` fires AFTER `RELEASE_LOCK` (listeners may email/log without holding the event lock) with `(promoted_row, event_id)`. REST DELETE /rsvps/{id} response gains additive `promoted: row|null` (admin-gated serializer); admin React app ignores the field for now — list state drains locally and the waitlist rows it shows are unaffected by promotion of others on the same filter... except the promoted row itself vanishes from a `waitlist`-filtered view without a refetch; accepted for this slice (row-level stale display only, counts endpoint always truthful).
34. (backend) DB-failure surfacing in `delete_and_promote()`: writes run under `suppress_errors(true)` and each statement's failure is judged by rows_affected + `last_error` (the create() pattern). DELETE with 0 affected rows AND a non-empty last_error => `eh_db_error` 500 (row untouched, not masked); promotion UPDATE with 0 affected rows: `last_error` non-empty => `eh_db_error` 500, empty => guard-blocked no-promotion (legitimate). A failed delete+ok promotion shape cannot exist (delete fails => early return; promotion failure => error even though the delete already committed — reported honestly, counts remain the truth).
35. (backend) RSVP cascade on event hard-delete: `before_delete_post` -> `Plugin::maybe_delete_event_rsvps()` -> `Rsvp_Repository::delete_all_for_event()` — gated on post type `eh_event` (revisions/other types/absent IDs exit query-less); trash/untrash never touch rows. `delete_all_for_event` degrades to 0 when the table doesn't exist yet (fresh install where wp-admin never ran). Not wired to ICS/CSV — those query live anyway. No DB version bump (no schema change).

39. (backend) Manage-booking tokens (ROADMAP 2.1) — design diverged from the roadmap's "signed token = hash of email+event+salt" sketch deliberately: an HMAC over email+event would (a) force the attendee's email into the manage URL (PII in server logs, browser history, proxies if opened off-device), and (b) make wp_salt a global forgery key — the same nonce salt Form_Guard trusts. Built instead: 32 random bytes per row (`random_bytes`), DB stores SHA-256 hash in `manage_token CHAR(64) NULL` (DB 1.3.0, indexed), raw token exists ONLY in the confirmation email link (`/?eh_manage=<token>`); `find_by_token()` gates on 64-hex plausibility before querying and normalizes the row with the hash stripped. Toggle `event_hub_confirmations` (default OFF — emails are load-bearing for token delivery, so the admin opts in deliberately; rows created while off simply have NULL tokens and stay admin-managed; pre-1.3.0 rows likewise). Notifier: plain-text wp_mail, `phpmailer_init` Timeout=10 per send, failures swallowed (send_confirmation returns bool; create_rsvp's 201 never depends on mail). Anonymous surfaces (REST POST /rsvp/cancel, admin_post cancel/rename) are token-bearer: without a session a cookie nonce is meaningless, so the permission callback resolves the row from the token itself (THREAT-MODEL T16); the no-JS admin_post forms still carry a per-action nonce from the rendered page for CSRF. Cancel goes through delete_and_promote() so §1.3 promotion + event_hub_rsvp_promoted fire identically to admin deletes; `promoted` in the REST body uses the public serializer (no email). unknown-token renders/404s share one generic message (no enumeration oracle). CSV/ICS untouched — tokens are management surface, not export surface; serialize paths never include manage_token.
40. (backend) RSVP window cutoffs (ROADMAP 2.4) — post meta `eh_rsvp_open_hours` / `eh_rsvp_close_hours`, hours before `eh_start`, digits-only strings (0 legal = at start; '' = no boundary), registered with the same `^$|^[0-9]+$` save-time schema as eh_capacity (BUG 5 pattern); `Rsvp_Repository::parse_hours()` is the read-side twin of that pattern and `rsvp_cutoffs()` the single verdict source (closed = at/after start−close_hours, inclusive; not_open = before start−open_hours). Verdicts live in the REPOSITORY, not Render_Blocks — the write guard in create() (409 `eh_rsvp_closed` / `eh_rsvp_not_open`, sitting beside eh_event_passed so every write surface is covered) and the render fold share one clock: Render_Blocks::summary() only translates the verdicts into `rsvpOpen` + additive `cutoffClosed`/`cutoffNotOpen` keys. Both boundaries gate going AND waitlist (a window that stays open for the waitlist alone would surprise organizers; cancellation is unaffected — it is not a new RSVP). Missing/unparseable eh_start ALWAYS reports open (same conservative rule as the passed-guard: never block on missing data; an inverted open>close configuration degrades to "closed from start−close_hours", the editor warns instead of rejecting). Closed/not-open cards render inert like past cards (count line + reason notice, no iAPI region — the write guard would 409 anyway); the pill gains a `Closed` state that beats capacity states; store.ts maps both 409s for the render→click race. No DB version bump (post meta only). Tests: `Rsvp_Cutoff_Test` (12 cases).
41. (backend) Guests/seats per RSVP (ROADMAP 2.3, DB 1.4.0) — `guests INT UNSIGNED NOT NULL DEFAULT 1` (dbDelta rides the existing CREATE TABLE; legacy rows inherit 1, so pre-1.4.0 behavior is byte-identical). Capacity math counts SEATS, not rows: `create()`'s INSERT…SELECT predicate and `delete_and_promote()`'s promotion guard both switched COUNT(*) → COALESCE(SUM(guests),0); `counts()['going']/['waitlist']` are seat totals (cards, bar, pill, JSON-LD, REST all stay truthful with zero call-site changes; `checkedIn` stays a ROW count — a party checks in as it arrives). Deliberate tradeoff: the guard compares booked-seats-before-write < capacity, NOT booked+own-party <= capacity — admitting a party of 4 into 2 remaining seats is possible (the flip/insert admits the ROW); enforcing party-fits-remaining inside SQL would reject-on-write for the front end every time seats < party (dead going button experience) — instead the button YARDSTICK stays seats<capacity and oversized parties self-select to the waitlist; documented in tests. Param contract: repository-level `guests` 1..MAX_GUESTS (10) rejects with 400 `eh_invalid_guests` (0 seats would silently under-count); REST sanitizes BEFORE the repository (clamp, so an out-of-range request never 400s — it clamps; the repo guard remains for direct/CLI callers). MAX_GUESTS is a public const shared by REST arg, render select loop, and tests. Seats picker: context.guests + actions.setGuests + POST body; admin React table gains a Seats column; CSV gains a Seats column (position: after Status); Notifier email + manage page gain a Seats line. No new routes; serializers (`rsvp` 201 echo, public list `guests` in private list only — no change to the public events payload). Tests: `Seats_Test` (10 cases) — capacity-on-seats invariant, waitlist bypass at any size, promotion guard on seats (incl. the old row-COUNT predicate would have overbooked case), legacy default=1, clamp, eh_capacity_full seat counts, empty-event unlimited.

43. (backend) Calendar block (ROADMAP 3.3) — `event-hub/event-calendar`, architecture deliberately diverged from the roadmap sketch ("fed by the events REST route"): NO REST is involved. One PHP render path renders the whole month inside `data-wp-router-region="event-hub-calendar"`; prev/next are real GET links (`?eh_month=YYYY-MM`) that work without JS, and with JS `actions.calendarNav` (deep-merged onto the shared `event-hub` store) preventDefaults and delegates to the CORE interactivity-router `actions.navigate()` (Context7-verified pattern: plain `data-wp-on--click` + `withSyncEvent` generator + `yield import('@wordpress/interactivity-router')`) — the router refetches and re-renders every router region in the response, so the client never rebuilds a grid and the render contract stays single-path (the #30 lesson applied to navigation). The head (nav links) sits OUTSIDE the grid body but inside the region so both swap together. Month semantics: an event belongs to the month its START falls in (spanning events keyed by start — standard calendar behavior, documented); window query is `eh_start BETWEEN [first 00:00:00, last-day 23:59:59]` in SITE time (stored meta is site-local wall-clock; GMT bounds + `gmt_offset` offset), 200-event cap with phpcs:ignore justification. BUG caught by the new boundary test before any release render: the first draft had the BETWEEN trim on the WRONG edge (−1s on the LOWER bound, open upper) — that leaks previous-month 23:59:xx starts AND captures next-month midnight exactly; fixed to trim the UPPER edge. Grid math: noon `DateTimeImmutable` anchors in `wp_timezone()` (DST-safe, month-overflow-safe), `$leading_blanks = (w − start_of_week + 7) % 7`, weekday headers from a fixed Sunday anchor (2023-01-01, timezone-independent weekday), today marker + "now" month all in site frame via `time() + gmt_offset*HOUR_IN_SECONDS` (never discouraged `current_time('timestamp')`). GET `eh_month` read is sanitize_text_field + strict `^\d{4}-(0[1-9]|1[0-2])$` regex → junk falls back to the attribute, then the current month (phpcs:ignore on the nonce sniff — read-only view selector). Editor preview is a static 4×7 grid (server-render dependency, mirrors #30's no-JS-honesty rule). `@wordpress/interactivity-router` is a WP CORE script-module external (verified in webpack output), never an npm dep; its TS surface is declared ambiently in `src/types.d.ts` (build seam). Tests: `Calendar_Block_Test` (11: precedence/regex, window boundaries incl. midnight edges + December wrap, drafts excluded, nav wrap, grid math under both start_of_week settings, leap February, same-day stacking, count text, empty month) + Stage-5 calendar probe (KSES-bypassed hostile title escaped into cell anchor; hostile `eh_month` survives). Harness finding (reported, unfixed): Stage5's 11+1 probes have NO `EH_STAGE5` skip gate — the file header claims "run with EH_STAGE5=1" but they execute in EVERY suite run (plain, stage 3, stage 5). Stricter than intended, never a coverage hole; wiring the gate is a behavior change awaiting approval. Tests: `Calendar_Block_Test` (11) + 1 Stage-5 probe.
44. (backend) Recurring events (ROADMAP 3.2) — architecture deliberately diverged from BOTH roadmap sketches ("parent + occurrence CPTs" and "series_id meta"): the seed IS the first occurrence. A series = any published `eh_event` with non-empty `eh_series_freq`; occurrences are real published child posts (`post_parent` = seed) that behave as ordinary events on every read surface — the survey of all five selectors (REST list, ICS all-feed, upcoming bar, calendar window, admin When-sort/picker) showed they ALL already query `eh_start` meta in SQL, so real child posts mean ZERO query changes anywhere, and each occurrence gets its own RSVP list by construction (RSVPs key on post ID). Four flat, pattern-guarded meta keys on the seed (BUG-5 discipline, registered in `Plugin::register_meta()`): `eh_series_freq` (REST enum `["",daily,weekly,monthly]`), `eh_series_interval` (`^$|^[0-9]+$`, read-side clamp 1..366), `eh_series_byweekday` (`^$|^[0-6](,[0-6])*$`, 0=Sun), `eh_series_until` (`^$|^[0-9]{4}-[0-9]{2}-[0-9]{2}$`, strict round-trip parse — `date_create_immutable_from_format(\"Y-m-d\")` inherits the current clock time for absent H:i:s, so validity = `createFromFormat` re-format byte-equality). **Additive-only invariant**: the engine NEVER edits or deletes children — they own RSVPs; changing the rule only adds future spawns (existing dates are the idempotency key, `existing_dates()` keyed Y-m-d); deleting a seed orphans children as normal events (documented UI copy). Horizon = last child (or today) + 6 months capped by `until`; MAX_SPAWN_PER_RUN=200 per run; twice-daily cron tick re-rolls open-ended series and heals missed spawns; deactivation unschedules. Spawn copies title/content/excerpt/author/venue/capacity/cutoffs/terms/thumbnail + recalculated eh_start/eh_end (duration carried), NEVER the four series keys (a child with freq would seed its own series — now also impossible by gate, below).
